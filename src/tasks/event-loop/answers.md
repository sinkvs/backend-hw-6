# Задание 1.1 — Предсказание порядка выполнения

## Предполагаемый порядок вывода:
1, 12, 6, 4, 5, 2, 3, 7, 11, 10, 9, 8

##  Объяснение (по шагам):

### 1. Синхронный код
- `1: sync start` ---> `12: sync end`
- Все остальное регистрируется в очередях, но не выполняется.

### 2. Микрозадачи - высший приоритет после синхронного кода
- `6: nextTick` - `process.nextTick` всегда выполняется первым, раньше Promise.
- `4, 5: promise.then` - выполняются следом, так как это микрозадачи.

### 3. Макрозадачи -  фазы Event Loop
- `2: setTimeout` - фаза Timers.
- `3: setImmediate` - фаза Check.
- `7: readFile` - фаза Poll (I/O). Чтение файла занимает время, поэтому Event Loop успевает обработать таймеры и immediate до получения данных от ОС.

### 4. Внутри I/O колбэка `fs.readFile`
- `7` - синхронный вывод внутри колбэка.
- `11, 10` - микрозадачи (`nextTick` ---> `Promise`).
- `9, 8` - макрозадачи. `setImmediate` (фаза Check) выполняется раньше `setTimeout`, который уходит в следующий тик Timers.

## 🔑 Выводы:
- **Microtasks vs Macrotasks:** Микрозадачи очищаются полностью перед переходом к следующей фазе макрозадач.
- **nextTick > Promise:** `process.nextTick` - его очередь обрабатывается до стандартных microtasks (Promise).
- **Фазы Event Loop:** Порядок макрозадач зависит от фазы цикла (Timers ---> Poll ---> Check). I/O-операции не блокируют поток, позволяя обрабатывать другие задачи.

## Задание 1.2 — I/O-bound vs CPU-bound

### Реальный результат запуска:
- CPU Task: 455.743ms (примерно полсекунды)
- I/O Task: 1.618ms
- setTimeout сработал с задержкой: планировали на 100мс, а выполнился после цикла.

### Почему так вышло:
- **CPU-задача** (цикл) — синхронная операция в главном потоке. Пока поток занят вычислениями, он не может переключиться на таймеры или запросы. Это **блокировка Event Loop**.

- **I/O-задача** (чтение файлов) делегирует работу операционной системе. Node.js отправляет запрос и сразу идет дальше. Когда файл прочитан, ОС возвращает результат через колбэк. Поток свободен - **Event Loop не блокируется**.

## Задание 1.3 — Блокировка Event Loop

### Проблема:
Синхронный цикл на 5 млрд итераций занимает единственный поток JS. Пока он работает, Event Loop не обрабатывает другие запросы, `/fast` ждет завершения `/slow`.

### Решение:
Цикл разбит на чанки по 100 млн. После каждого чанка вызывается `setImmediate`.

### Как работает:
`setImmediate` откладывает продолжение цикла до фазы Check. В этот момент Event Loop обрабатывает накопившиеся запросы (например, `/fast`), затем возвращается к скрипту. Итог - сервер отвечает на легкие запросы даже во время тяжелых вычислений.

## Задание 2.1 — CommonJS vs ESM

### Реализация:
- `math.cjs` / `demo.cjs` - CommonJS: `module.exports` / `require()`
- `math.mjs` / `demo.mjs` - ESM: `export` / `import`

### Ответы на вопросы:
**1. Можно ли в .cjs использовать `import`?**  
Нет, т.к. расширение `.cjs` жестко указывает на CommonJS, синтаксис `import` в таких файлах не работает без доп. настроек.

**2. Можно ли в .mjs использовать `require`?**  
Нет, `.mjs` всегда трактуется как ESM-модуль, а `require()` доступен только в CommonJS.

**3. Что такое `"type": "module"` в package.json?**  
Это поле меняет поведение по умолчанию для `.js` файлов, они начинают интерпретироваться как ESM. При этом `.cjs` и `.mjs` сохраняют свое поведение независимо от этой настройки.

## Задание 3.1 — Первый Fastify-сервер

### Реализация:
- Сервер на порту 3000 с тремя роутами: `/`, `/health`, `/time`
- Graceful shutdown через обработчики SIGINT/SIGTERM

### Как работает:
- `/` - базовый ответ для проверки подключения
- `/health` - мониторинг: статус + аптайм в секундах
- `/time` - демонстрация динамических данных (вычисляются в момент запроса)
- `fastify.close()` - завершает текущие запросы перед остановкой, не обрывая соединения
